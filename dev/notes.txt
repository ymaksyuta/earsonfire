Architecture notes
===================
Pins down decisions made during the App.jsx split so they don't have to
be re-derived from the diff later. Update this file when the shape
described here changes.

Layering (application/src/)
----------------------------
core/         instrument- and screen-agnostic engine pieces. Nothing in
              here should import from instruments/ or screens/.
                midiNotes.js       MIDI note number <-> VexFlow key / frequency
                notation.js        renders a track to VexFlow SVG (renderScore);
                                   also owns rest insertion and measure
                                   detection — see "Rests and measures" below
                usePlayback.js     Web Audio transport (play/pause/stop/step)
                                   for one track
                loadMidiFile.js    parses an uploaded file into
                                   {tracks, ppq, timeSignature}; also resolves
                                   track names that live on a separate empty
                                   track from their notes (see "Track naming"
                                   below)
                combineTracks.js   merges several selected tracks' notes into
                                   one tick-sorted stream (no chording)
                resolveMonophonic.js  reduces an overlapping note stream (the
                                   result of combineTracks, or a single dense
                                   track) down to one note at a time — see
                                   "Monophonic reduction" below
              arrayUtils.chunk() is currently unused (nothing chunks by a
              fixed item count anymore now that notation.js groups by
              measure instead) but left in place as a small generic utility.

instruments/  one subfolder per instrument, plus the registry
              (instruments/index.js). Each instrument exports:
                id                  unique string, also the <select> value
                label               display name
                getFingering(midi)  -> fingering object | null (shape is
                                       instrument-defined, not shared)
                FingeringDiagram    React component: { label, fingering }
                                    -> JSX
              'none' is a built-in registry entry with no fingering
              support. To add an instrument (recorder, calimba, guitar,
              piano - see roadmap.txt): add instruments/<name>/ with its
              own fingering data + diagram component, export an object
              matching the shape above, add it to instruments/index.js.
              Nothing in core/ or screens/ should need to change.

screens/      the two screens concept.txt describes.
                SelectionScreen.jsx  file/track/strategy setup, plus a
                                     read-only score preview; owns the
                                     fixed-part/scrollable-part layout
                                     split described under "Screen
                                     layout" below
                TrainingScreen.jsx   score + playback + fingering; owns
                                     usePlayback and the notation render
                                     effect, since both only matter here.
                                     Also owns instrument selection now
                                     (moved here from SelectionScreen —
                                     see "Screen layout")

App.jsx       top-level state only (file, filename, tracks, selected
              track indices, track order/priority, simultaneous-note
              strategy, instrument, tempo, playback mode, which screen
              is active) and wiring props into the two screens. No
              VexFlow/Web Audio/fingering logic should live here - if it
              starts to, that logic belongs in core/ or instruments/
              instead.

State ownership
----------------
App.jsx:                  tracks / fileName / selectedIndices /
                           trackOrder / strategy / instrument / tempo /
                           playbackMode / screen
TrainingScreen (via
  usePlayback):            playing / paused / currentNoteIndex
TrainingScreen (local):    showTempo (tempo popup open/closed — see
                           "Screen layout"; ephemeral UI state, not
                           worth lifting to App.jsx since nothing needs
                           to remember it across a screen change)
"Where are we in the score right now" lives with playback, not App,
since it only exists while training and resets whenever the track
changes (usePlayback resyncs on every `track` reference change).

The `track` object passed into TrainingScreen is always
combineTracks(...) piped through resolveMonophonic(...), even when
exactly one track is selected — there's no separate "single track"
code path. A plain { notes, name } shape is enough; nothing downstream
needs an actual @tonejs/midi Track instance; combineTracks converts to
plain note objects rather than passing the original instances through.

Score vs. capture vs. acoustic
--------------------------------
See dev/concept.txt for the up-to-date wording; summary of the reasoning:

Today the app only has SCORE input: a MIDI file, loaded as the reference
material shown with recommended fingering. It is NOT player input, even
though earlier notes called it "midi input" - that name was a source of
confusion (a MIDI *file* is a score; a MIDI *instrument* is a capture
device) and concept.txt has been reworded to avoid it.

Two kinds of player input are planned, neither implemented yet:
  capture   direct note events - MIDI-in from a real instrument, or
            sensor data from an emulator/ESP32 board translated into note
            events. Same shape either way (a stream of note-on/off), so
            the training loop shouldn't need to care which one it's
            getting from.
  acoustic  pitch/onset detected from real sound (microphone), used as a
            fallback when no capture device is available.

When capture/acoustic land, expect: a new core/ module owning that event
stream (something like core/useCapture.js, mirroring usePlayback's
shape), and probably a small addition to the instrument interface
(e.g. evaluateInput(expectedFingering, capturedState)) - not a rework of
the core/instruments/screens boundaries above.

Known trade-offs
-----------------
- Tempo changes only take effect on the next Play (usePlayback samples
  `tempo` into a ref at start time) because notes are all pre-scheduled
  as Web Audio oscillators; there's no live clock to rescale mid-flight.
- renderScore has no note-count cap — it always renders the whole
  track/combined selection, producing a wide SVG for a long piece
  rather than truncating (a real ~1700-note track benchmarked at
  ~1.5s render time; a note cap existed here before and was removed
  because silently hiding part of the score is worse than a slower
  render). If very large files become a real problem, virtualize or
  paginate rather than reintroducing a silent cap.

Playback modes: score track vs. audio track (core/usePlayback.js)
-------------------------------------------------------------------
usePlayback takes two separate note streams rather than one:
  scoreTrack   always App.jsx's `track` (combined + monophonic-resolved
               selection). Drives the note cursor, and therefore the
               notation highlight and fingering diagram, off its own
               timeline — regardless of what's actually audible.
  audioTrack   whatever should actually be scheduled as oscillators.
               TrainingScreen picks this based on `playbackMode`
               ('mine' -> scoreTrack itself, 'others' -> App.jsx's
               `otherTrack`, the combined complement of the selected
               tracks).
Both streams come from the same source file, so they already share one
absolute timebase (seconds) — no rescaling needed to keep them in
sync. Playback stops once whichever of the two streams' last note ends
later has finished, so a longer backing track isn't cut short by a
shorter monophonic score or vice versa.

`otherTrack` (App.jsx) is combineTracks() over every track NOT in
selectedIndices, deliberately NOT run through resolveMonophonic — it
only ever feeds the 'others' backing-track mode, where keeping the
original chords/polyphony is the point (contrast `track`, which must
be monophonic for the score/fingering diagram to make sense). App.jsx
resets playbackMode back to 'mine' whenever otherTrack ends up empty
(nothing loaded, or every track selected), so the toggle can't get
stuck pointed at silence.

Rests and measures (core/notation.js)
--------------------------------------
The score renders one musical measure per stave (this app is a single
horizontally-scrolled reel of staves, not paginated/wrapped lines, so
"fit N measures per line" doesn't apply the way it would in a real
score layout). Measures come from the file's time signature
(loadMidiFile reads midi.header.timeSignatures[0], defaulting to 4/4)
— only the initial signature is used for the whole track; a mid-piece
meter change isn't handled.

Rests are inserted wherever there's a real gap between notes (or before
the first note, as a pickup rest), split at every measure boundary the
gap crosses. A gap segment that exactly fills a whole measure renders
as a literal whole rest — the standard notational convention for "this
measure is empty" regardless of time signature — rather than whatever
duration the raw tick count would otherwise snap to. Gaps under a 32nd
note are treated as note-off/note-on articulation slop and dropped,
not drawn.

Both rest and note durations are approximated to the nearest
power-of-two value (whole/half/quarter/8th/16th/32nd) via
ticksToDuration(); this is not a measure-accurate rhythm
transcription, and a note whose performed duration runs past a barline
isn't split into tied notes — it's grouped into the measure it starts
in and just visually extends from there. Tightening this would mean
teaching notation.js to split/tie notes across barlines, which hasn't
been needed yet.

A stave's width is measured from its own content
(Formatter.preCalculateMinTotalWidth) rather than a fixed value, and
the formatter is told to justify to exactly that measured width (never
the wider MIN_STAVE_WIDTH floor) - asking it to spread notes across
unused floor space was what caused the barline-overflow bug fixed
earlier (a trailing item's glyph, especially a rest, could land past
the stave's right edge into the next stave). Unused floor space is
safely left as blank trailing margin instead.

Track naming (core/loadMidiFile.js)
-------------------------------------
Some MIDI exports (older Cakewalk/Band-in-a-Box-style sequencers, seen
in media/Vabank.mid) put an instrument's name on its own otherwise-
empty track immediately preceding the track that actually holds its
notes, rather than naming the note-bearing track itself. parseMidiFile
resolves this: a note-bearing track with no name of its own borrows the
nearest preceding name it can find, walking backward over empty tracks
but stopping the moment it hits another track that already has notes
(so a name never crosses an instrument boundary). Names also get a
trailing-NUL/control-byte strip, since MIDI text events are C-strings
under the hood and often carry one.

Multi-track selection and monophonic reduction
-------------------------------------------------
The Selection screen lets the user check any number of tracks (not
just pick one). App.jsx merges them with combineTracks (concatenate +
sort by tick, no chording — see that file's own comments) and then
reduces the merged stream to one note at a time with resolveMonophonic
— unless the 'none' strategy is picked, in which case nothing is
reduced and notation.js renders the real polyphony instead (see
"Polyphonic rendering" below). Every *instrument* is still assumed
monophonic (no instrument here can play more than one note at once,
which is why fingering is hidden in polyphonic mode) — 'none' just
means the score itself is allowed to show more than one part at a
time, e.g. to read the other parts while playing your own.

resolveMonophonic's strategy is chosen via a combo box on the
Selection screen (core/resolveMonophonic.js exports STRATEGIES for
it). Each entry also carries a `hint` string, a one-line, human-
readable explanation shown under the combo box — see "Screen layout"
below for why that hint has a fixed-height slot rather than just
appearing/disappearing.
  shorter      IMPLEMENTED. Walks the tick-sorted notes keeping one
               "held" note; any later note overlapping it is a
               conflict, resolved by keeping whichever of the two has
               the shorter duration (the loser is dropped entirely,
               not truncated). Handles chains of more than two mutually
               overlapping notes correctly since `held` keeps getting
               re-challenged by each new arrival.
  priority     IMPLEMENTED. Ranks the tracks by their position in the
               voice checklist (App.jsx's `trackOrder` — every track
               index, reorderable via the ▲▼ buttons next to each
               checkbox on the Selection screen); when two notes
               overlap, the one from the higher (earlier-listed) track
               wins, regardless of duration. combineTracks tags every
               note with sourceTrackIndex for this. Replaced an earlier
               unimplemented 'primary' strategy (a single designated
               "primary" track) — priority-by-list-order does the same
               job without needing a separate primary-track picker.
  none         IMPLEMENTED. No reduction at all — resolveMonophonic
               just returns combineTracks' output unchanged. App.jsx
               derives a plain `polyphonic` boolean (`strategy ===
               'none'`) and passes it to notation.js and TrainingScreen
               rather than having either of those know strategy ids —
               see "Polyphonic rendering" below for what it triggers.
  autodetect   NOT YET IMPLEMENTED. Intended to pick the harmonic "key
               note" of a simultaneous cluster (e.g. a chord's root),
               which needs actual chord analysis. Falls back to
               'shorter' for now so picking it in the UI doesn't leave
               unresolved overlaps.

Polyphonic rendering (core/notation.js)
------------------------------------------
When `polyphonic` is true, renderScore takes a different path
(renderPolyphonic instead of renderSingleVoice) that draws one VexFlow
Voice per source track, all layered onto the same stave per measure via
Formatter.joinVoices — "several parts in a single stave", not several
staves. The two paths share everything else (rest-insertion,
measure-grouping, stave sizing).

Getting simultaneous notes to line up (left-aligned, per the original
ask) needs no special-case code: VexFlow positions tickables by their
cumulative tick offset within a voice, and shares that positioning
("TickContext") across every voice passed to the same
Formatter.joinVoices call. Two notes from different voices that
genuinely start at the same musical instant end up in the same
TickContext and therefore get the same x coordinate automatically, as
long as each voice's own rests accurately fill its silences (see
withRests' `padToTicks` below) — there's no explicit "align these"
step in the code.

Splitting one note stream into voices (splitBySourceTrack) groups by
sourceTrackIndex — one voice per selected track, not per chord. A
single track that itself contains internal chords (several notes at
the exact same tick, all with the same sourceTrackIndex) is NOT
detected or grouped into one VexFlow chord; those notes fall into the
same voice sequentially, which will visually arpeggiate a same-track
chord instead of stacking it. This mirrors combineTracks' pre-existing
"no chording" stance, just now visible in a second place — fixing it
for real would mean detecting same-tick/same-track note clusters and
building multi-key StaveNotes for them, which hasn't been needed yet
since no currently-supported instrument produces that kind of source
data on its own track.

Every voice must span the same number of measures for
Formatter.joinVoices to accept them (see the TickMismatch pitfall
below), even when one selected track's notes end earlier than
another's — withRests' `padToTicks` parameter handles this: after a
voice's own notes run out, it fills the remaining ticks out to the
overall combined ending (rounded up to a full measure) with trailing
rests, the same way an internal fully-silent measure already got a
whole rest. Only the polyphonic path uses this; renderSingleVoice's
one voice has nothing to align against, so it never pads past its own
last note.

Pitfall worth remembering: VexFlow's Voice.getTotalTicks() is computed
purely from the *declared* `{num_beats, beat_value}` passed to `new
Voice(...)`, never from the tickables actually added to it — and
Formatter.joinVoices throws a TickMismatch RuntimeError if the voices
being joined don't report equal getTotalTicks(). The original
single-voice code declared `num_beats: vfNotes.length` (an arbitrary
per-group item count, not a real time value) — harmless there since
only one voice was ever joined at a time, but it meant two voices for
the same measure, differing only in how many notes/rests they happened
to contain, would be declared as spanning different total ticks and
fail to join. buildVoice fixes this by declaring the track's real time
signature (e.g. [4, 4]) for every voice regardless of content, so the
comparison is always trivially satisfied; `setStrict(false)` (kept from
before) separately relaxes each voice's own internal "did ticksUsed
exactly fill totalTicks" check against ticksToDuration's power-of-two
rounding, unrelated to the cross-voice comparison.

Fingering (TrainingScreen) assumes exactly one active note at a time,
which doesn't hold once there can be several simultaneous notes, so
TrainingScreen skips rendering the fingering panel entirely whenever
`polyphonic` is true — checked once, in TrainingScreen, rather than
teaching every instrument's FingeringDiagram to handle a null/multi-note
"current" state.

Tap-to-select (core/notation.js + core/usePlayback.js)
-----------------------------------------------------------
Every rendered note (not rests) gets a click handler on its own SVG
element (attachClickHandlers, called after voice.draw() since
getSVGElement() only returns something once the note is actually in the
DOM), wired to `onNoteClick(item.noteIndex)` — the same index space as
activeIndex/noteX, so a tap can move the cursor exactly like a step/play
action would. This applies to both rendering paths (single-voice and
polyphonic) since the click wiring lives in the shared drawStaves pass,
not in either path's own code.
TrainingScreen passes usePlayback's new `selectNote(index)` as
onNoteClick: it stops any playback in progress (jumping around while
oscillators are already scheduled against a fixed timeline wouldn't
make sense — same reasoning stepNote already followed) and sets
currentNoteIndex directly to the tapped note, clamped to a valid index.
SelectionScreen's read-only preview does NOT wire up onNoteClick —
there's no cursor there for a tap to move.

Screen layout
--------------
Both screens follow the same rough shape — caption, then a toolbar
row, then the score, then whatever else that screen needs — but each
implements it a little differently since Selection needs a scrollable
list and Training needs playback controls. Written down here since the
shape isn't obvious just from reading either component in isolation.

Selection screen (fixed part + scrollable part):
  The screen splits into two pieces so the controls you need before
  starting (load a file, preview the score, hit Start) never scroll out
  of view, while the part that can get long (the voice checklist) gets
  its own scroll area instead of pushing everything else down the page.
    .select-fixed   caption ("Ears on Fire"), the toolbar row (Load…
                    button + current filename + MIDI export button),
                    the read-only score preview, and the Start training
                    button. Natural height, never scrolls.
    .select-scroll  voice checklist (with the ▲▼ reorder buttons),
                    the strategy combo box and its hint, and the
                    version footer. Takes up whatever vertical space is
                    left and scrolls internally if its content doesn't
                    fit; the version footer sits at the bottom of this
                    area (via margin-top: auto) rather than being
                    pinned to the viewport, so it's simply the last
                    thing you scroll to if there's a lot of content.
  This only works full-height on this one screen, so SelectionScreen
  toggles a `screen-selection` class on <body> in a mount/unmount
  effect rather than that layout being baked into the shared .wrap
  class Training also uses — Training still just scrolls as one normal
  page.
  The strategy hint (see STRATEGIES[].hint above) is always rendered,
  never conditionally omitted, in a slot with a fixed min-height long
  enough for the longest hint text. Otherwise switching strategies
  would grow/shrink that slot and visibly shift the voice checklist
  above it — small, but the kind of jitter that makes a UI feel
  unpolished on a phone screen where everything's already tight.
  The file input itself is visually hidden; a <label htmlFor="fileInput">
  styled as a button ("Load…") triggers it instead, sitting next to a
  plain text span showing the current filename (or a "No file loaded"
  placeholder) — a real file input's own filename text can't be styled
  or truncated consistently across browsers, so this route was more
  reliable than trying to reskin the native control directly.

Training screen (caption row + playback toolbar):
  Top row: Back button, the voice's name (was called trackName in
  props — think of it as this screen's "caption"), and instrument
  selection. Instrument selection lives here now, not on Selection —
  it only ever affects the fingering diagram at the bottom of this
  screen, so there's no reason to decide it before seeing the score.
  Playback toolbar: previously three separate rows (transport buttons,
  a full-width part-selection text button, a permanently-visible tempo
  slider) collapsed into one row to save vertical space:
    - transport buttons (⏮ / ▶ or ⏸ / ⏹ / ⏭) unchanged
    - part selection (mine vs. others/backing) is now one icon-only
      button (🎵 or 🎧) instead of a full-width labelled button; the
      label moved into its `title` tooltip
    - tempo is now an icon button showing the current multiplier
      (e.g. "⏱ 1.00×") that opens a small popup containing the slider,
      instead of the slider always taking up its own row. The popup
      closes on any pointerdown outside it (a document-level listener
      added only while it's open) — there's no explicit close button.
  Both changes are about density, not behavior: the same
  onPlaybackModeChange/onTempoChange callbacks fire the same way, just
  from smaller controls.
